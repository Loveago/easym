# SECTION 2 — PRODUCT DEFINITION

amaMomoApp is a multi-network mobile money agent assistant.

The application provides one interface through which an agent can manage transactions across MTN, AT Money and Telecel.

The application is intended to reduce repetitive manual USSD navigation, make transactions easier to initiate, and maintain accurate transaction records.

It should feel like a proper mobile money agent terminal rather than a generic banking application.

The most important principle is:

**An agent should be able to open the application, select a network, select a transaction type, enter the necessary information and follow a clear transaction process without unnecessary navigation.**

# SECTION 6 — USSD AUTOMATION ENGINE

This is a critical part of amaMomoApp.

Do not implement USSD automation as a collection of hardcoded text fields and arbitrary delays.

Build a configurable, state-driven USSD automation engine.

The engine must understand the current USSD prompt, determine the expected response and move through the correct transaction flow.

## 6.1 Technical implementation

Use:

- Kotlin.
- Android Telephony APIs where supported.
- Android Accessibility Service where permitted and necessary.
- Coroutines.
- StateFlow.
- ViewModel.
- Room database.

Respect Android permissions and platform restrictions.

USSD interaction capabilities vary by Android version, manufacturer, SIM configuration and carrier.

Do not assume every Android device permits programmatic access to all USSD responses.

Where a system API is unavailable, use an appropriate user-assisted interaction flow.

Do not bypass Android permission systems or silently control the user's phone.

## 6.2 USSD engine architecture

Create these independent components.

### A. UssdLauncher

Responsibilities:

- Load the selected network profile.
- Load the requested transaction flow.
- Retrieve the verified USSD entry code.
- Check SIM availability.
- Initiate the session using an approved Android mechanism.
- Report initiation errors.

### B. UssdSessionManager

Responsibilities:

- Create a unique session ID.
- Track session state.
- Maintain current flow step.
- Prevent overlapping transactions.
- Track session timeout.
- Support cancellation.
- Prevent accidental duplicate execution.

### C. UssdPromptObserver

Responsibilities:

- Receive USSD responses using the permitted mechanism.
- Extract visible dialogue text.
- Normalize whitespace.
- Normalize supported character variations.
- Pass the observed prompt to the flow controller.

### D. UssdPromptMatcher

Responsibilities:

- Compare the observed text against expected prompts.
- Support exact matching.
- Support normalized matching.
- Support configurable regular expressions.
- Support multiple recognized variants.
- Detect unexpected prompts.
- Detect provider errors.
- Detect session termination.

### E. UssdFlowController

Responsibilities:

- Determine the current flow step.
- Check the observed prompt.
- Determine the next action.
- Substitute customer and transaction variables.
- Request manual input when required.
- Send the appropriate response when permitted.
- Advance to the next state only after the expected prompt is observed.

### F. UssdInputHandler

Responsibilities:

- Handle dynamic values.
- Format phone numbers.
- Format monetary amounts.
- Validate entered values.
- Prevent empty inputs.
- Prevent accidental wrong-network values.

### G. UssdConfirmationHandler

Responsibilities:

- Detect confirmation screens.
- Display transaction details.
- Require appropriate authorization.
- Never bypass provider confirmation requirements.

### H. UssdResultDetector

Responsibilities:

- Recognize successful responses.
- Recognize failed responses.
- Recognize pending responses.
- Recognize insufficient-balance responses.
- Recognize invalid-recipient responses.
- Recognize timeout responses.
- Recognize unexpected responses.

### I. UssdRecoveryManager

Responsibilities:

- Handle timeouts.
- Handle network interruptions.
- Handle unexpected menu changes.
- Handle cancelled sessions.
- Handle application interruptions.
- Preserve transaction state.
- Prevent automatic duplicate financial operations.

## 7.2 USSD flow template

Implement a structured configuration similar to this:

```yaml
network: MTN
transaction_type: CASH_IN

flow_id: MTN_CASH_IN
version: 1

entry_code: VERIFY_FROM_AGENT_SIM

timeout_seconds: 90

steps:

  - id: START
    type: INITIATE_USSD
    code: VERIFY_FROM_AGENT_SIM
    next: MAIN_MENU

  - id: MAIN_MENU
    type: MATCH_PROMPT
    expected_prompt: VERIFY_FROM_AGENT_SIM
    action: SEND_VERIFIED_MENU_OPTION
    next: ENTER_CUSTOMER_NUMBER

  - id: ENTER_CUSTOMER_NUMBER
    type: MATCH_PROMPT
    expected_prompt: VERIFY_FROM_AGENT_SIM
    action: SEND_VARIABLE
    variable: customer_phone
    next: ENTER_AMOUNT

  - id: ENTER_AMOUNT
    type: MATCH_PROMPT
    expected_prompt: VERIFY_FROM_AGENT_SIM
    action: SEND_VARIABLE
    variable: amount
    next: REVIEW_TRANSACTION

  - id: REVIEW_TRANSACTION
    type: MATCH_PROMPT
    expected_prompt: VERIFY_FROM_AGENT_SIM
    action: REQUIRE_CONFIRMATION
    next: FINAL_RESULT

  - id: FINAL_RESULT
    type: MATCH_RESULT
    success_prompts:
      - VERIFY_FROM_AGENT_SIM

    failure_prompts:
      - VERIFY_FROM_AGENT_SIM

    pending_prompts:
      - VERIFY_FROM_AGENT_SIM
```

This is an implementation template, not a claim that the actual MTN menu follows this exact sequence.

The final sequence must be populated from verified live agent USSD sessions.

## 7.3 Prompt matching

Each expected prompt must support several variants.

Example configuration:

```json
{
  "step_id": "ENTER_CUSTOMER_NUMBER",
  "expected_prompts": [
    "VERIFIED_PROMPT_VARIANT_1",
    "VERIFIED_PROMPT_VARIANT_2"
  ],
  "match_mode": "NORMALIZED_TEXT",
  "input_type": "PHONE_NUMBER",
  "next_step": "ENTER_AMOUNT"
}
```

The system must not continue merely because a screen appeared.

It must verify that the observed prompt matches the expected prompt for the current step.

If no match is found:

1. Stop automated input.
2. Display the observed prompt to the user where possible.
3. Mark the session as requiring manual intervention.
4. Do not guess the next menu option.
5. Preserve the transaction as pending or unknown as appropriate.

# SECTION 21 — PAYSTACK SUBSCRIPTIONS

Paystack must be the application's subscription payment provider.

Do not implement Google Play Billing.

Do not use Google In-App Purchases.

## Backend payment process

1. User selects a subscription plan.
2. Android sends an authenticated request to the backend.
3. Backend validates the user and plan.
4. Backend initializes Paystack payment.
5. Backend returns the checkout URL.
6. Android opens Paystack Checkout.
7. User completes payment.
8. Paystack sends a webhook.
9. Backend verifies webhook signature.
